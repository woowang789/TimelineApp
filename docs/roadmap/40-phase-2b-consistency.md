## 4. 기술 상세

이 Phase가 구현하는 마스터 결정의 실행 관점 요약. **결정을 재론하지 않는다** — 각 결정의 근거·버린 대안은 마스터 해당 절이 원본이다.

### 4.1 Read-Your-Own-Write — §7.7

Kafka는 Phase 3에서 도입되지만, **비동기 지연이 생기는 순간 깨질 구조를 지금 분리해 둔다.**

```
글 작성 요청
  ├─ 본인 타임라인에 ZADD          (동기 — 응답 전 완료)
  └─ 나머지 팔로워 fan-out         (fan-out 워커로 위임)
  → 응답
```

- self-follow 행(§4.3)이 있으므로 팔로워 목록에 본인이 포함된다. 본인은 이미 동기 처리했으므로 fan-out 대상에서 **한 줄로 제외**한다.
- 이 fan-out 워커 분리가 2b-10(Virtual Thread 실험)의 실험대이자, Phase 3에서 Kafka 컨슈머로 치환될 자리다.
- 검증은 지연을 실제로 만든 상태여야 의미가 있다: fan-out 워커에 5초 지연을 인위 주입하고 본인 글 즉시 노출을 확인한다.

### 4.2 언팔로우 = C(방치) — §7.8

결정은 이미 내려져 있다: **C 채택.** Phase 2b의 일은 구현이 아니라 **그 결정을 수치로 방어하는 실측 표**를 만드는 것이다.

| 방식 | 비용 (실측 대상) | 비고 |
|---|---|---|
| A. 즉시 제거 | 언팔 1회당 타임라인 500개 스캔 + ZREM 지연 | 실측 후 폐기 |
| B. 읽기 시 필터 | 매 조회 팔로잉(최대 500) 대조 → 조회 p99 증가폭 | 읽기 최적화 목적과 정반대 — 실측 후 폐기 |
| **C. 방치** | **0** | 상한 500으로 자연 소멸. **본선 채택** |

- A/B는 실측 전용 브랜치에서만 존재한다. 본선에는 코드가 남지 않는다(C는 구현이 없는 것이 구현이다).
- 단서(§7.8): 차단(block)이었다면 C가 성립하지 않는다 — 이 프로젝트에 차단이 없어서 성립한다. 표와 함께 이 단서를 기록한다.

### 4.3 팔로우 백필 — §7.9

- **N=20**: 타임라인 첫 페이지 크기와 같다. "팔로우 직후 첫 페이지에 그 사람 글이 보인다"가 체감의 전부다.
- **비동기 `@Async`**: §7.7과 달리 즉시성 요구가 약하다. Phase 3에서 Kafka 이벤트로 치환된다.
- **인플루언서 제외**: 대상의 `is_influencer == true`면 백필하지 않는다. 인플루언서는 Phase 3에서 읽기 시 머지되므로 백필 자체가 불필요하다 — Hybrid의 부수 효과로 도배 문제가 사라지는 지점.
- ZADD는 멱등이라 이미 타임라인에 있는 postId를 다시 넣어도 오염이 없다. 백필 후에도 상한 500(`ZREMRANGEBYRANK`)을 유지한다.

### 4.4 재조회 상한 3회 — §7.5

- 25개 조회 → 삭제 필터 → 부족 시 마지막 postId 커서로 재조회, **상한 3회 = 총 75개 스캔.**
- `75(1−p) ≥ 20 → p ≤ 0.73`: 삭제율 73%까지 20개가 채워진다. 그 이상이면 있는 만큼 반환 + `hasNext=true` — 클라이언트는 `nextCursor`로 이어서 요청한다.
- 전제: negative cache(tombstone 60초, Phase 2a §7.13 구현분). 없으면 대량 삭제가 그대로 DB 부하로 증폭된다.
- 측정은 §9.5의 시나리오 표 그대로 `normal` 코호트에서, 0/30/50/70/90% 구간으로.

### 4.5 카운터 Source of Truth = DB — §7.4

- 쓰기: `likes` 행 삽입 + `UPDATE posts SET like_count = like_count + 1`을 **한 트랜잭션** — 원자적 UPDATE라 동시 갱신이 유실되지 않는다.
- 읽기: `post:{postId}` 캐시(TTL 1시간) 경유 — 타인에게 최대 1시간 stale은 **명시적으로 허용된 부정확성**이다.
- 본인: `DEL post:{postId}` 후 갱신값 직접 반환 — 즉시 반영.
- Redis 카운터(`like:count:{postId}`)는 만들지 않는다(§5에서 폐기 확정).
- 검증은 유실이 실제로 없음을 보이는 동시성 테스트다: 동시 좋아요 100건 → `like_count == 100`.

### 4.6 동등성 검증 — §9.4 (+ §7.3)

- **임의 사용자 100명: Pull 쿼리 결과 20건 == Push 타임라인 조회 결과 20건, postId 시퀀스 일치.** self-follow 행(§4.3) 덕분에 두 경로의 결과 집합이 같아지는 것이 전제다.
- Testcontainers 통합 테스트로 **CI 상시 실행** — Phase 2 이후 모든 변경의 회귀 방지선.
- **fan-out 강제 중단 → 재처리 → 동등성 유지**가 §7.3(Sorted Set 멱등성, at-least-once로 충분)의 실증이다. 이 테스트가 Phase 3에서 Kafka 재시도/DLQ 논리의 근거가 된다.
- 부하 테스트 직후 샘플링해 **불일치율(%)을 성능 지표와 나란히 기록**한다 (2b-11).

### 4.7 Virtual Thread 실험 — §3 · §8 Phase 2b

- **범위: fan-out 워커 한정. Tomcat은 건드리지 않는다.** Java 21을 택한 근거(§3)를 계획으로 실행하는 자리다.
- fan-out 워커의 작업은 팔로워 청크 DB 조회 + Redis ZADD 파이프라인 — blocking I/O라 스레드 모델 차이가 드러날 후보다.
- 비교: 동일 부하에서 플랫폼 스레드풀 vs VT의 fan-out 처리량·완료 지연.
- `-Djdk.tracePinnedThreads=full`로 pinning(synchronized 블록에 의한 캐리어 스레드 고정)을 관측한다 — **"써봤다"가 아니라 "한계를 안다"가 되는 지점.**

### 4.8 재측정 — §9.2 / §9.3

- 쟁점 구현(재조회 상한, 동기 ZADD, 백필)이 읽기/쓰기 경로에 얹은 비용이 M3(Push·warm)를 후퇴시키지 않았는지 확인한다.
- M3와 동일 조건·동일 프로토콜(스냅샷 복원, 3회 중앙값, `dropped_iterations == 0`, open model)로 재실행해야 비교가 성립한다.
- 회귀가 있으면 `@Timed` 구간 분해로 원인을 귀속한다 — "느려졌다"가 아니라 "어느 구간이 몇 ms 늘었다"로 기록한다.
