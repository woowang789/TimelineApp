## 1. 목표와 완료 조건

같은 기능의 3번째 구현이다. Push의 남은 문제 — **팔로워가 많은 계정이 글을 쓰면 응답이 오래 걸린다**(마스터 §8 Phase 2b) — 를
Kafka 비동기화와 Hybrid(임계치 5,000)로 해소하고, 그 비용(머지)을 M4와 임계치 3종 비교로 수치화한다.

| # | 목표 | 완료 조건 (검증 가능한 형태) |
|---|---|---|
| G1 | fan-out을 Kafka로 분리 | 글 작성 API가 이벤트 발행 후 **즉시 응답**한다. 작성 p99가 팔로워 수와 무관해지고(팔로워 500명 계정 vs ~18명 계정 비교), fan-out 완료 지연(lag)이 별도 지표로 기록된다 |
| G2 | at-least-once + 멱등의 실증 | 컨슈머를 강제 중단 후 재처리해도 §9.4 동등성 테스트가 통과한다 (불일치율 0%) |
| G3 | Read-Your-Own-Write 유지 (§7.7) | 컨슈머 지연 5초 인위 주입 상태에서 작성 직후 본인 글 즉시 노출 테스트가 녹색이다 |
| G4 | Hybrid 구현 (§7.2) | 팔로워 5,000 미만 Push / 이상 머지. 승격 경계 테스트(승격 전후 글의 **중복 0 · 누락 0**)와 Hybrid 코호트를 포함한 동등성 검증 CI가 녹색이다 |
| G5 | M4 측정 | `docs/perf/m4.md` 커밋 — §9.3 프로토콜 준수(3회 반복 중앙값, `dropped_iterations = 0`, 스냅샷 복원, 코호트 고정) |

### W14 (2026-11-23 ~ 11-29) — Hybrid (임계치 5,000)

| # | 규모 | 작업 | 상세 | 검증 |
|---|---|---|---|---|
| 3.10 | 0.5일 | 승격 로직 | 팔로우 처리 트랜잭션에서 `follower_count`(self-follow 제외)가 임계치 5,000 도달 시 `is_influencer = true`, `influencer_since = now()`. **단방향 — 강등 없음** (§7.2 결정 2). 임계치는 설정값으로 두어 3.18~3.19의 비교 측정에 재사용 | 통합 테스트: 5,000번째 팔로우에서 승격 + `influencer_since` 기록, 이후 언팔로우가 발생해도 플래그 유지 |
| 3.11 | 0.5일 | 더미 데이터 일괄 승격 배치 | 더미는 벌크 삽입이라 팔로우 이벤트를 타지 않았다. `follower_count >= 임계치`인 사용자를 일괄 승격하는 배치(임계치 파라미터화). `influencer_since`는 **더미 게시글 시간창 이전(데이터셋 최소 게시글 시각 또는 Snowflake epoch 2025-01-01)으로 백데이팅**한다(마스터 부록 B) — 승격 시각을 현재로 잡으면 기존 인플루언서 글 전부가 머지 범위(`postId > snowflakeOf(influencer_since)`) 밖이 되어 M4의 머지 비용 측정이 공동화된다. 폴백 Pull로 캐시에 들어간 글과의 중복은 머지 dedup(3.13)으로 흡수. **실제 승격 인원을 로그로 남겨 §7.2 표(110명/1,110명/10명)와 대조 기록** | 임계치 5,000으로 실행 시 S(10)+A(100) 계층 승격 확인, `influencer_since`가 데이터셋 최소 게시글 시각 이전임 확인, 승격 인원 로그가 남음 |
| 3.12 | 0.5일 | 인플루언서 fan-out 제외 | 발행자에서 작성자 `is_influencer = true`면 팔로워 fan-out 이벤트를 발행하지 않는다. **본인 동기 ZADD는 유지**(§7.7). 이 시점부터 Push 대상 팔로워 최대치가 임계치로 제한되어 청크 최대 10개가 성립한다 (§7.11) | 통합 테스트: 인플루언서 글 작성 후 팔로워 타임라인에 ZADD 없음 + 본인 타임라인에는 있음 + Kafka 메시지 0건 |

## 4. 기술 상세

마스터의 결정을 실행 관점에서 재서술한다. 원본과 다르게 읽히면 원본(§ 표기)이 맞다.

### 4.1 실행 구성 — 모니터링을 내리고 Kafka를 올린다 (§3)

8GB 제약에서 Kafka 1.2G 자리는 Prometheus/Grafana를 내려야 나온다. `async` 프로파일은
MySQL 2G + Redis 1.5G + Kafka 1.2G = 4.7G (Docker 할당 5G). 따라서 이 Phase의 계측은
**Actuator(`/actuator/metrics` 스냅샷) + 애플리케이션 로그 + k6 클라이언트 지표**로 수행하고,
fan-out lag는 이벤트 발행 시각을 실어 컨슈머에서 계산한다(작업 3.9). Grafana 대시보드는 쓸 수 없으며,
이 제약은 리포트에 명시한다(§9.3).

### 4.2 Kafka fan-out 파이프라인 (§7.11 · §7.3 · §5-6)

```
글 작성 → 본인 동기 ZADD → 커밋 → [팔로워 500명 청크 × N] 발행(키 없음) → 즉시 응답
                                          │
컨슈머: 청크 수신 → active:users 파이프라인 ZSCORE(청크당 1회) → 7일 이내만 ZADD + 상한 500 트림
        실패 시 재시도 3회 → DLQ
```

- **파티션 키를 지정하지 않는 근거(§7.11)**: 타임라인은 Sorted Set이고 score가 postId(=시간)다.
  **ZADD는 도착 순서와 무관하게 같은 결과를 만든다.** 순서 보장을 포기해도 잃는 것이 없고,
  그 대가로 파티션이 균등해져 핫 파티션이 원천 차단된다. soft delete라 ZREM 이벤트가 없어
  ZADD/ZREM 역전도 없다. Hybrid 적용 후 Push 대상 팔로워 최대치는 임계치(5,000) → 청크 최대 10개.
- **at-least-once로 충분한 근거(§7.3)**: `ZADD timeline:1001 9982 9982`는 몇 번을 실행해도 같다(멱등).
  청크 중간에 죽어 재전달돼도 중복이 생기지 않는다. 그래서 exactly-once도, 컨슈머 측 중복 제거 테이블도
  만들지 않는다. 이 논리는 작업 3.6(중단·재처리 → 동등성 통과)으로 실증한다.
- **활성 필터(§5-4, §5-6)**: 팔로워 목록은 캐시하지 않고 `(followee_id, follower_id)` 커버링 인덱스로
  DB에서 청크 조회한다(비동기 경로라 수십 ms 조회는 문제가 아니다). 필터는 청크당 파이프라인 ZSCORE 1회 —
  `ZINTERSTORE`(임시 키 누수 위험)도 Lua(이 규모에서 이득 없음)도 쓰지 않는다.

### 4.3 Read-Your-Own-Write는 Kafka 경로 밖에 있다 (§7.7)

본인 타임라인 ZADD는 작성 요청 안에서 동기로 끝난다. Kafka가 5초 밀려도 내 글은 즉시 보인다.
self-follow 행이 있으므로 fan-out 대상 목록에서 본인을 한 줄로 제외한다(이미 처리했으므로).
Kafka 도입이 이 경로를 건드리지 않았음을 지연 5초 주입 테스트 **재실행**으로 확인한다(작업 3.7).

### 4.4 Hybrid — 임계치 5,000, 단방향 승격, `influencer_since` 경계 (§7.2)

- **분기**: 팔로워 5,000 미만 → Push(fan-out). 5,000 이상(influencer) → fan-out 없음, 조회 시
  `내 타임라인 캐시` + `팔로우한 인플루언서의 최근 글` 머지.
- **승격은 단방향**이고 `influencer_since`를 기록한다. 강등을 지원하면 "인플루언서 기간 글의 소급 백필"
  문제가 새로 생기고, 단방향이면 히스테리시스도 불필요하다.
- **머지 범위는 `postId > snowflakeOf(influencer_since)`**: 승격 이전 글은 이미 Push되어 캐시에 있고
  이후 글만 머지 대상이므로 중복도 누락도 없다. 다만 승격 트랜잭션과 동시에 진행 중이던 작성/폴백
  (폴백 Pull은 인플루언서 글도 캐시에 채운다)이 경계에 걸릴 수 있어 **머지 결과의 postId dedup을
  안전망으로 둔다** — dedup은 이론상 불필요해야 정상이고, 발동 빈도가 높으면 경계 버그다.
- **백필과의 맞물림(§7.9)**: 인플루언서는 백필하지 않는다 — 애초에 Push 대상이 아니라 머지되므로,
  팔로우 시 도배 문제가 자동으로 사라진다.
- **남는 한계(README에 명시)**: 작성 빈도를 보지 않는다. 팔로워 5,000 × 일 50회 계정이
  팔로워 20,000 × 월 1회 계정보다 위험한데 이 설계로는 걸러지지 않는다.

### 4.5 측정 — M4와 임계치 3종 (§9 · §7.2)

M4는 M0~M3와 같은 프로토콜(§9.1 open model, §9.3 고정 조건)로 잰다. 다른 점은 두 가지다:
① 서버 계측이 Actuator+로그뿐이다(4.1) ② 조회 경로에 머지 구간이 추가되어 `@Timed` 분해에
머지 항목이 늘어난다(작업 3.15). 임계치 비교는 임계치가 유일한 변수가 되도록
스냅샷 복원 → 승격 배치 → 동일 시나리오를 3종에 반복하고(작업 3.16의 자동화),
결과는 **읽기 머지 비용 vs 쓰기 지연의 양방향 표**로 제시한다 — 임계치는 비용을 없애는 것이 아니라
옮길 뿐이라는 §7.2의 논리를 수치로 보이는 것이 목적이다.

- fan-out 이벤트 발행자(청크 500 · 키 없음 · 인플루언서 분기) / 컨슈머(활성 필터 + ZADD + 트림) / 재시도·DLQ 핸들러
- 승격 로직(팔로우 트랜잭션) + 더미 일괄 승격 배치(임계치 파라미터)
- Hybrid 머지 조회(`snowflakeOf` 경계 + dedup) — 기존 2단계 조회·재조회 상한 3회에 통합
- 백필(§7.9)의 Kafka 이벤트 이관
- 통합 테스트: 멱등 재처리(3.6) · RYOW 지연 5초(3.7) · 승격 경계 중복/누락(3.13) · 활성 필터(3.3) · 동등성 Hybrid 코호트(3.14)

**인프라 · 스크립트**
- `compose.async.yml` 검증·보정분 (Phase 0 작성분 기반)
- k6 시나리오: `k6/m4-*.js` (warm 조회 / 혼합 98:2 / fan-out 단독 / 인플루언서 작성)
- `Makefile`의 `bench-m4` 타깃 (`THRESHOLD` 파라미터, §9.6 "한 명령")

**측정 · 문서**
- `docs/perf/m4.md` — §9.7 템플릿, M3 대비 비교 포함
- `docs/perf/m4-threshold.md` — 임계치 3종 양방향 비교 표 + 실측 승격 인원
- `docs/perf/raw/m4/run{n}.json`, `docs/perf/raw/m4-threshold-{500|20000}/run{n}.json` — W15 원시 k6 결과 커밋 (측정별 하위 디렉토리 규칙, 20~50 문서와 동일)

- (W16) README·성능 리포트 갱신분, git 태그 `v3-hybrid`, [`./00-overview.md`](./00-overview.md) 현황판 갱신

## 6. 리스크와 대응 (이 Phase 고유)

| # | 리스크 | 대응 |
|---|---|---|
| 1 | **모니터링 없이 측정한다** — Kafka 자리를 위해 Grafana/Prometheus를 내렸다(§3) | 계측 경로를 W13에 먼저 구축(작업 3.9: lag 타이머 + 로그). 측정 시 Actuator 스냅샷과 `docker stats`를 함께 저장하고, 이 제약을 리포트 환경 서식에 명시(§9.3) |
| 2 | **임계치 3종 측정의 비용** — 매 측정이 "스냅샷 복원 + 승격 배치 + 워밍"을 요구해 W15가 빠듯하다 | 3.16의 `make bench-m4 THRESHOLD=` 자동화를 측정보다 먼저 완성. 3회 반복 중앙값 원칙(§9.3)은 줄이지 않는다 — 반복을 줄이면 관문 통과가 아니다 |
| 3 | **더미 일괄 승격의 경계** — `influencer_since`를 배치 실행 시각으로 잡으면 기존 인플루언서 글 전부가 머지 범위 밖이 되어 M4의 머지 비용 측정이 공동화된다 | `influencer_since`를 **더미 게시글 시간창 이전으로 백데이팅**한다(작업 3.11, 마스터 부록 B) — 기존 글 전체가 머지 범위에 들어온다. 폴백 Pull이 캐시에 넣은 인플루언서 글과 머지의 중복은 dedup(3.13)이 흡수하며, 동등성 검증(3.14)이 최종 심판이다 |
| 4 | **컨슈머 lag 중 동등성 검증 오탐** — fan-out이 소화되기 전 비교하면 일시적 불일치가 정상인데 결함으로 보인다 | 동등성 테스트는 컨슈머 lag=0(idle) 확인 후 실행하도록 테스트 픽스처에 대기 조건을 넣는다. lag 상태의 사용자 체감은 3.21에서 별도로 실측한다 |
| 5 | **승격 인원이 §7.2 표와 다르게 실측될 수 있다** — 임계치 3종을 500/5,000/20,000으로 정정하면서(마스터 §7.2) 표(1,110/110/10명)와 더미 분포의 산술이 확정·일치해 이 리스크는 해소됐다 | 산술 확정으로 해소됨. 다만 실측 병기는 유지한다 — 승격 배치가 실측 인원을 로그·리포트에 병기하고(작업 3.11, 3.18), 비교 표의 해석은 실측 인원 기준으로 쓴다 |
| 6 | **보너스 Phase의 일정 침식** — Phase 3가 늦어져도 잃을 본편이 없지만, 어중간한 반영이 완결 산출물을 오염시킬 수 있다 | 중단 시 README·리포트에는 **완결된 단위만** 반영한다(W13 Kafka만 완료면 Hybrid 서사는 싣지 않는다). `v3-hybrid` 태그는 관문(M4+임계치 비교) 통과 시에만 만든다 |
