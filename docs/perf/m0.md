# M0 — Pull, 인덱스 없음

> 측정 지점 정의: 마스터 §9.2 / 로드맵 [20-phase-1-baseline.md](../roadmap/20-phase-1-baseline.md) §4.4
> 작업: P1-11(본 측정) · P1-12(이 문서)
> **M0의 "인덱스 없음"은 `posts`에 조회용 보조 인덱스가 없다는 뜻이다.**
> PK·FK·`UNIQUE(follower_id, followee_id)` 등 스키마 제약은 유지되며,
> FK 제약의 부산물인 `fk_posts_author`(author_id 단일 컬럼) 인덱스는 존재한다.

이 측정의 성공 기준은 낮은 지연이 아니다. **최악 baseline을 신뢰 가능한 방법으로 확정하는 것**이다.
p99가 수 초 단위로 나오는 것이 정상이며(§8 Phase 1), 그 수치가 이후 M1~M4 개선 주장의 분모가 된다.

## 측정 방법

### 프로토콜 (§4.5 준수)

```
매 런:  snap-m0 볼륨 복원
     →  앱 기동 (buffer pool cold)
     →  cold 참고치 3회 기록          ← 복원 직후 대표 사용자 1명, 단건 조회
     →  워밍업: posts 풀스캔 + follows 풀스캔 + fk_posts_author 인덱스 스캔 + API 30회
     →  warm 사다리 본 측정          ← 보고 수치는 전부 이 구간
```

- 3회 반복 · **중앙값 보고 + 최대-최소 편차 병기**
- 사용자는 5,000명 코호트(`heavy` 1,000 / `normal` 2,000 / `light` 2,000)에서만 추출, 시나리오별 고정
- cold / warm 두 조건 모두 기록(Phase 1에는 Redis 타임라인 경로가 없으므로 buffer pool 기준)

### 여기까지 오는 데 실패한 시도 세 가지

숨기지 않고 적는다(§10). 세 번 다 **재측정 전량 폐기**로 이어졌다.

**1) 집계 p50/p99로는 포화점을 읽을 수 없었다.**
1차 heavy 측정에서 사다리 전체의 집계 지표를 보니 붕괴 구간(상위 단계)이 분포를 지배해
"어느 RPS에서 꺾였는가"를 판독할 수 없었다. **stage 태그로 단계별 하위 메트릭을 분해**한 뒤
전량 재측정했다. 이 리포트의 결과 표가 단계별인 이유다.

**2) cold buffer pool에서 사다리를 시작했다 — §4.5 위반.**
첫 단계의 지연이 쿼리 비용이 아니라 디스크 적재 비용을 재고 있었다. cold 상태를 없애는 대신
**cold 참고치를 별도로 남기고 + 풀스캔 워밍업을 프로토콜에 추가**한 뒤 재측정했다.
cold를 버리지 않은 이유는 §4.5가 두 조건 모두 기록하라고 규정하기 때문이다.

**3) `setup()`의 로그인이 p99를 오염시켰다.**
사전 발급을 위한 로그인 요청이 타임라인 요청과 같은 메트릭에 섞여 있었다.
**endpoint 태그로 하위 메트릭을 분리**해 해결했다. 같은 오염이 JFR에도 존재한다
(원인 분석 "JFR" 항 참조) — 계측 도구가 바뀌어도 같은 함정이 반복된다는 게 이 실패의 교훈이다.

### 부하 생성기 격리 한계 (§9.3 — 숨기지 않고 밝힌다)

k6는 호스트에서 8코어를 애플리케이션과 공유한다. **완전한 격리는 불가능하다.**
측정 중 5초 폴링으로 CPU를 기록해 경합 여부를 판단 가능하게 남겼다.

| 코호트 | java 평균 | k6 평균 |
|---|---|---|
| `heavy` | 44% | 7.6% |
| `normal` | 68% | 5.5% |
| `light` | 76% | 12.2% |

출처: `{코호트}-run1.cpu.log`. **k6 경합은 낮았다** — 부하 생성기가 수치를 지배한 구간은 없다.
heavy에서 java CPU가 오히려 가장 낮은 것(44%)이 병목이 앱 CPU가 아님을 시사한다.

### 5. buffer pool 히트율 — 하향 트리거 판정

| 코호트 | 측정 구간 차분 히트율 | 판정 |
|---|---|---|
| `heavy` / `normal` / `light` 전 런 | **≥ 99.9%** | 게이트(95%) 통과 — **하향 트리거 미발동** |

- 히트율 = `1 − (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)`
- `SHOW GLOBAL STATUS`는 서버 기동 이후 누적이라 복원 직후 cold 읽기가 섞인다.
  따라서 **런 전/후 차분**으로 산출했다(예: `heavy-run1.hitrate.txt` — delta reads 12 / delta read_requests 5,626,308).
- **게시글 300만을 그대로 유지한다.** 200만 하향(§8 · §4.6)은 발동하지 않았다.
- 이 수치의 더 중요한 함의: **병목은 디스크 I/O가 아니다.** 데이터는 메모리에 다 있는데도 느리다.
  남는 후보는 CPU와 정렬이며, 원인 분석이 그쪽을 가리킨다.

## 원인 분석

대상 쿼리는 §4.3의 Pull SQL 그대로다.

```sql
SELECT p.* FROM posts p
JOIN follows f ON p.author_id = f.followee_id
WHERE f.follower_id = :userId
  AND p.id < :cursor
  AND p.is_deleted = false
ORDER BY p.id DESC LIMIT 25
```

### 1. `EXPLAIN` (옵티마이저 추정 · heavy user 1)

| 순서 | 테이블 | 접근 | rows | Extra |
|---|---|---|---|---|
| 1 | `f` | `uk_follows_follower_followee` **ref** | 501 | `Using index; Using temporary; Using filesort` |
| 2 | `p` | `fk_posts_author` **ref** | 30.7 | **`filtered 5.00%`** |

- `f` 쪽은 커버링 인덱스로 끝난다(§4.1 설계 의도대로). **문제는 `f`가 아니다.**
- `Using temporary; Using filesort` — `ORDER BY p.id DESC`를 받아줄 인덱스가 없어
  **조인 결과 전체를 모아 정렬**해야 한다는 신호다.
- 옵티마이저 추정 행수 = 501 × 30.7 × 5.00% ≈ **770행**.

### 2. `EXPLAIN ANALYZE` (실측)

| 코호트 | 루프 수 | 루프당 행 | **정렬 입력 행수** | **총 실행 시간** |
|---|---|---|---|---|
| `heavy` | 501 | 29.9 | **14,963** | **409ms** |
| `normal` | 101 | 30.3 | **3,061** | **65.5ms** |
| `light` | 11 | 29.3 | **322** | **6.1ms** |

heavy 실행 계획(무경합 · 최상 warm):

```
Covering index lookup on f  (501행, 0.3ms)
  → Nested loop
    → Index lookup on p using fk_posts_author  (29.9행 × 501루프)
      → Sort: p.id DESC, limit 25
```

**세 코호트의 실행 계획은 동일하다. 다른 것은 정렬 입력 행수뿐이고, 시간은 그 행수에 비례한다.**

```
light  →  normal :   322 →  3,061행 (9.5배)  ·  6.1 → 65.5ms (10.7배)
normal →  heavy  : 3,061 → 14,963행 (4.9배)  ·  65.5 → 409ms (6.2배)
```

팔로잉 수가 늘면 느려지는 이유가 "JOIN이 비싸서"가 아니라 **"정렬해야 할 입력이 그만큼 늘어서"**임을
이 비례 관계가 보여준다. 병목의 이름은 JOIN이 아니라 **filesort**다.

### 3. 추정 vs 실측 — 19배 괴리

| | 행수 |
|---|---|
| `EXPLAIN` 추정 | 770 |
| `EXPLAIN ANALYZE` 실측 | **14,963** |
| 괴리 | **19배** |

원인은 `filtered 5.00%`다. 옵티마이저가 `p.id < :cursor AND p.is_deleted = false`의 선택도를
통계 없이 5%로 어림했는데, 실제로는 거의 전부가 통과한다(`is_deleted`는 대부분 false이고,
커서는 최신부터 조회하면 사실상 전 구간을 연다).

**"`EXPLAIN`은 추정이고 `EXPLAIN ANALYZE`는 실측이며, 둘의 차이 자체가 분석거리다"(§3)의 실증이다.**
추정만 봤다면 "770행이면 인덱스 없어도 괜찮겠는데"라는 잘못된 결론에 도달했을 것이다.

### 4. slow log

| 지표 (heavy 쿼리) | 값 |
|---|---|
| `Rows_examined` p50 | **15,606** |
| `Rows_examined` max | 15,884 |
| 반환 행 수 | 25 |
| 검사/반환 비 | **약 600배** |

`EXPLAIN ANALYZE`의 14,963행과 독립적으로 같은 크기를 가리킨다 — 두 도구가 서로를 교차 검증한다.
**25건을 돌려주려고 1만 5천 행대(실측 정렬 입력 14,963 / slow log `Rows_examined` 15,606)를 읽고 정렬한다**는 것이
M0의 한 문장 요약이다.

### 5. JFR

- 조회 구간에서 **애플리케이션 CPU 샘플이 미미하다.** 병목은 앱이 아니라 **MySQL 측 + 큐잉**이다.
  (CPU 로그에서 heavy의 java 사용률이 44%로 세 코호트 중 가장 낮았던 것과 일치한다.)
- hot method 1위가 **BCrypt 48%**로 잡히지만 이건 **`setup()` 로그인 구간의 오염**이다.
  타임라인 조회 부하와 무관하다. k6에서 p99를 endpoint 태그로 분리해야 했던 것과 **완전히 같은 문제의
  JFR 판**이며, 계측 주의점으로 남긴다 — 프로파일러는 "언제부터 언제까지"를 알아서 잘라 주지 않는다.

### 6. heavy 붕괴 메커니즘 — p50 30초는 쿼리 시간이 아니다

무경합 서버 내부 실행 시간은 **409ms**(최상 warm)인데 클라이언트 p50은 **30초**다.
`클라이언트 지연 − 서버 내부 지연 = 큐잉 시간`(§9.3)이므로 이 차이는 거의 전부 큐잉이다.

```
409ms (무경합 내부) — 최상 조건
  ↓ 실전 warm 단건은 0.05 ~ 8.8s로 편차 (페이지 캐시 상태에 따라)
  ↓ open model의 랜덤 도착 → 버스트
  ↓ 처리 중 커넥션 점유 (쿼리가 수 초를 잡고 있다)
  ↓ HikariCP 풀 10 소진
  ↓ 대기 30초 타임아웃 → 500 연쇄
  ↓ open model은 실패해도 주입을 멈추지 않는다 → 회복 불가
```

이 사슬이 결과 표의 모양을 설명한다.

- **p50 ≈ 30,000ms의 정체는 쿼리 실행 시간이 아니라 커넥션 대기 타임아웃(30s)이다.**
  s1~s4에서 p50이 30,416 ~ 31,636ms로 30초에 수렴하고 편차가 s4에서 ±43ms까지 줄어드는 것이 그 증거다 —
  쿼리 시간이라면 이렇게 한 값으로 모이지 않는다. **타임아웃 상수를 재고 있는 것이다.**
- **주입량을 늘려도 p50이 나빠지지 않는다**(35,976 → 30,416ms). 이미 포화라 더 나빠질 여지가 없다.
  포화점을 찾는 사다리인데 **최저 단계에서 이미 포화 이후**라는 뜻이다.
- 실패율이 런마다 97.5 / 93.5 / 83.9%로 흔들리는 것도 이 사슬의 진입 시점 차이로 설명된다.

**여기서 커넥션 풀을 키우는 것은 답이 아니다.** 풀을 키우면 500이 줄어드는 대신 대기열이 길어지고,
15,000행 정렬이라는 근본 비용은 그대로다. M0가 지목하는 것은 풀 설정이 아니라 쿼리다.

## M1이 충분하지 않았던 이유

**해당 없음 — M0가 이 프로젝트의 첫 측정이다.** 이 절은 M1 이후의 리포트(`m1.md`)에서 채워진다.

M0가 준비하는 것은 그 반대 방향의 근거다. M1이 "인덱스만으로는 한계가 있었다"의 증거가 되려면(§9.2),
**인덱스가 없는 상태의 수치가 먼저 확정되어 있어야 한다.** 이 문서가 그 역할이다.

## 남은 문제

**25건을 반환하려고 14,963행을 정렬한다**(heavy · `EXPLAIN ANALYZE` 실측).
`ORDER BY p.id DESC`를 받아 줄 `posts` 보조 인덱스의 부재가 1차 병목이다.

근거를 한 줄로 모으면:

| 도구 | 관측 | 함의 |
|---|---|---|
| `EXPLAIN` | `Using temporary; Using filesort` | 정렬을 인덱스로 처리하지 못한다 |
| `EXPLAIN ANALYZE` | 정렬 입력 14,963행 / 409ms · 시간 ∝ 행수 | 비용의 주체는 정렬 |
| slow log | `Rows_examined` p50 15,606 vs 반환 25 | 낭비 배율 600배 |
| buffer pool | 히트율 ≥ 99.9% | I/O가 아니다 — CPU/정렬이다 |
| JFR | 앱 CPU 샘플 미미 | 앱이 아니다 — DB + 큐잉이다 |

### 다음 (P1-13 → M1)

인덱스 후보 2종을 **실측으로 비교**해 채택한다(§4.1 후보 규정 · 로드맵 P1-13).
파일은 이미 작성해 두었고, 적용·측정은 P1-13에서 한다.

| 후보 | 인덱스 | 마이그레이션 | 노리는 것 |
|---|---|---|---|
| A | `(author_id, id DESC)` | `V2__add_posts_index_candidate_a.sql` | author별 `id` 역순 접근을 인덱스로 → filesort 제거 |
| B | `(author_id, is_deleted, id DESC)` | `V3__swap_candidate_a_to_b.sql` | A + `is_deleted` 필터까지 인덱스로 커버 |

두 후보의 실행 계획·수치 비교표가 M1 리포트의 입력이 된다.
탈락안도 되돌림 마이그레이션으로 이력에 남긴다 — **그 이력 자체가 실패한 시도의 기록**이다(§3).

> 다만 인덱스가 filesort를 없애더라도 **"팔로잉 수만큼 인덱스를 훑는" 구조 자체는 남는다.**
> heavy는 여전히 501개 author를 순회해야 한다. 그 남은 비용의 크기가 곧
> "인덱스만으로는 한계가 있었다"(§9.2)의 근거가 될 것이며, M1 측정 전에는 예단하지 않는다.
