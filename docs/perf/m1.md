# M1 — Pull + 복합 인덱스

> 측정 지점 정의: 마스터 §9.2 / 로드맵 [20-phase-1-baseline.md](../roadmap/20-phase-1-baseline.md) §4.4
> 작업: P1-13(인덱스 후보 비교) · P1-14(본 측정) · P1-15(이 문서)
> **M0([m0.md](./m0.md))과의 차이는 `posts` 인덱스 하나뿐이다.**
> 애플리케이션 코드·데이터셋·k6 스크립트·프로토콜은 동일하고, 바뀐 것은 스키마 한 줄이다.

M1의 성공 기준도 낮은 지연이 아니다. **"인덱스만으로 얼마나 개선되는가"에 대조군을 만드는 것**이다(§9.2).
이 숫자가 없으면 Phase 2a의 Push 전환은 "느려서 캐시를 넣었다"는 근거 없는 문장이 된다.

결론을 먼저 적는다.

- 인덱스는 **heavy 코호트를 붕괴에서 건져냈다** — 실패율 83.9~97.5% → **0%**, p50 30초대 → **184~273ms**.
- 그러나 **p99 200ms에는 닿지 못했다** — heavy는 최저 주입(2 RPS)에서도 p99 522ms다.
- 남은 격차의 원인은 행당 비용이 아니라 **읽고 정렬하는 행수 자체**이며, 그 행수는 인덱스를 바꿔도 변하지 않았다
  (정렬 입력 14,963행 — M0과 **동일**).

개선의 귀속이 불가능해진다(§9.2).

### 이 측정의 유일한 변수 — `posts` 복합 인덱스

```sql
CREATE INDEX idx_posts_author_deleted_id_desc ON posts (author_id, is_deleted, id DESC);
```

P1-13에서 후보 2종을 **각각 적용해 실측 비교**한 뒤 후보 B를 채택했다.

| | 후보 A | 후보 B (**채택**) |
|---|---|---|
| 인덱스 | `(author_id, id DESC)` | `(author_id, is_deleted, id DESC)` |
| 마이그레이션 | `V2__add_posts_index_candidate_a.sql` | `V3__swap_candidate_a_to_b.sql` |
| heavy 단축 부하 실측 | 기준 | **동률** — p50 차이 ±10ms 이내 |
| 실행 계획 차이 | `is_deleted`를 행마다 테이블에서 확인(Filter 단계 존재) | **`is_deleted`가 인덱스 조건으로 흡수 — Filter 단계 소멸** |
| Sort 제거 | **실패** | **실패** |

**동률인데 B를 택한 이유**는 지금의 수치가 아니라 앞으로의 조건이다. 더미 데이터에는 삭제 글이 없어
`is_deleted` 필터가 아무것도 걸러내지 않는다. soft delete가 실제로 쌓이는 Phase 2a 이후에는
A가 행마다 지불하는 테이블 접근이 그대로 비용이 된다. **동률일 때는 조건이 나빠질 쪽을 기준으로 고른다.**
(이 결정은 마스터 부록 B "posts 채택 인덱스 (P1-13)"에 등재했다. V3 상태가 최종이며 V4는 만들지 않는다.)

탈락안 A도 지우지 않고 `V2 → V3` 이력으로 남겼다 — **되돌림 마이그레이션 자체가 실패한 시도의 기록**이라는
것이 Flyway를 넣은 이유다(§3).

> **부수 실측 — InnoDB FK 인덱스 재바인딩.**
> V3의 최초안은 `DROP(A) → CREATE(B)` 순서였고 **`ERROR 1553`으로 실패했다.**
> V2가 `author_id` 선행 인덱스를 만드는 순간 InnoDB가 자동 생성 인덱스 `fk_posts_author`를 조용히 제거하고
> FK를 후보 A에 재바인딩했기 때문이다. `CREATE(B) → DROP(A)` 순서로 고쳤다.
> M0의 실행 계획에 등장하던 `fk_posts_author`는 M1에는 존재하지 않는다.
> (부록 B "InnoDB FK 인덱스 재바인딩" 등재 · V2/V3 주석에 과정 보존)

### 부하 모델

open model 2종, M0과 같은 구조다. **사다리 수치만 올렸다.**

| 시나리오 | executor | 주입 |
|---|---|---|
| `saturation` | `ramping-arrival-rate` | 코호트별 사다리, **단계당 1m**, 3회 반복 |
| `slo` | `constant-arrival-rate` | 1,000 RPS · 5분 · `startTime: '2m'` |

| 코호트 | M0 사다리 | **M1 사다리** | `preAllocatedVUs` |
|---|---|---|---|
| `heavy` | 1, 2, 3, 4, 6 RPS | **2, 5, 10, 15, 20 RPS** | 600 (M0: 400) |
| `normal` | 2, 5, 10, 20, 40 RPS | **5, 10, 20, 40, 80 RPS** | 600 |
| `light` | 10, 25, 50, 100, 150 RPS | **10, 25, 50, 100, 150 RPS** (동일) | 600 |

- 사다리를 올린 것은 §9.1의 "구조는 동일하게 유지하되 사다리 수치만 예상 포화점에 맞춰 조정" 규정에 따른 것이다.
  **M0 사다리(heavy 1~6 RPS)를 그대로 쓰면 M1의 포화점을 지나치지 못해 "어디서 꺾이는가"에 답할 수 없다.**
- `light`는 M0과 사다리가 완전히 같다 — 그래서 아래 "M0 대비 개선 폭"에서 전 구간 1:1 대조가 가능하다.
- **`dropped_iterations == 0` 게이트: 보고한 9개 유효 런 전부 충족한다.**
  (`slo`는 예외 — "결과 · slo" 참조. 그 미달 자체가 결과다.)

## 측정 방법

### 프로토콜 (§4.5 준수)

```
매 런:  snap-m1 볼륨 복원
     →  앱 기동 (buffer pool cold)
     →  cold 참고치 3회 기록          ← 복원 직후 대표 사용자 1명, 단건 조회
     →  워밍업: posts 풀스캔 + posts 보조 인덱스 스캔 + follows 풀스캔 + API 30회
     →  warm 사다리 본 측정          ← 보고 수치는 전부 이 구간
     →  ★ 다음 런까지 3분 휴지        ← M1에서 추가된 단계 (아래 "실패한 시도 5")
```

- 3회 반복 · **중앙값 보고 + 최대-최소 편차 병기**
- 사용자는 5,000명 코호트에서만 추출, 시나리오별 고정. VU는 매 반복 코호트에서 **무작위 1명**을 뽑아
  커서 없는 첫 페이지를 조회한다(`k6/timeline-read.js`)
- cold / warm 두 조건 모두 기록

> 워밍업의 보조 인덱스 스캔은 인덱스 이름을 박지 않고 `author_id` 조건으로 유도한다.
> M0는 `fk_posts_author`, M1은 `idx_posts_author_deleted_id_desc`로 지점마다 이름이 다르고,
> `FORCE INDEX`로 이름을 고정하면 없는 지점에서 `ERROR 1176`으로 워밍업이 깨진다(실측 · `scripts/bench.sh` 주석).
> **meta.txt의 워밍업 설명 문자열은 M0 시절 문구(`fk_posts_author`)가 그대로 남아 있다** —
> 실제로 스캔된 것은 M1의 채택 인덱스다.

### 여기까지 오는 데 실패한 시도 — 4, 5, 6

m0.md의 1~3(집계 지표 / cold 시작 / `setup()` 오염)에 이어진다. 숨기지 않고 적는다(§10).
**세 번 다 재측정 전량 폐기로 이어졌고, 셋 다 쿼리가 아니라 측정 환경의 문제였다.**

**4) k6의 VU별 사본이 호스트를 스왑으로 밀어넣었다.**
`dropped_iterations`를 없애려고 `preAllocatedVUs`를 2,000까지 올렸다. k6의 init 컨텍스트는 **VU마다** 실행되므로
`cohorts.json` 파싱과 `setup()` 토큰 배열의 사본이 VU 수만큼 생겼고, k6 프로세스 메모리가 수백 MB로 부풀었다.
8GB 호스트에서 그 대가를 치른 것은 mysqld였다 — **스왑으로 밀려나면서 2 RPS부터 p50이 수십 초로 나왔다.**
쿼리는 그대로인데 buffer pool warm이라는 전제 자체가 깨진 것이다. **3런 폐기.**
코호트 로딩을 **`SharedArray`**(프로세스당 1부, 전 VU 공유)로 바꿔 해결했다.
§9.3이 명시하라고 한 "부하 생성기 격리 불가"가 이론이 아니라 **수치를 실제로 뒤집은 실증 사례**다.

**5) 팬리스 M1 Air의 서멀 스로틀링이 포화 구간을 최대 8배 과대평가했다.**
연속 측정 4시간이 넘어가자 **같은 조건 재실행이 갈수록 나빠졌다** — normal 코호트가 M0보다 나쁘게 측정되는
지점까지 갔다. 인덱스를 넣었는데 느려질 수는 없으므로 측정을 의심했다.
**40분 쿨다운 후 검증 런**으로 재현성을 판정했다.

| 구간 | 열 오염 상태의 재현성 |
|---|---|
| 안정 구간(낮은 주입) | ±30% 이내로 재현 — 오염이 잘 드러나지 않는다 |
| **포화 구간(높은 주입)** | **최대 5~8배 과대평가** — heavy 20 RPS p50 **1,955ms → 235ms** |

**포화 구간은 열 상태에 극도로 민감하다.** 붕괴 직전의 시스템에서는 코어 클럭 저하가 큐잉으로 증폭되기 때문이다.
오염 런 3개를 폐기하고 **런 사이 3분 휴지**를 프로토콜에 추가한 뒤 **전 코호트를 재측정**했다.
이 리포트의 수치는 전부 3분 휴지 프로토콜 아래에서 나온 것이다(각 `meta.txt`의 `run 사이 휴지: 3분`).

**6) 측정 전 호스트 상태 리셋도 조건의 일부다.**
Docker Desktop을 재시작해 VM이 쥐고 있던 메모리를 반환시켰다(**호스트 스왑 5.4GB → 3.2GB**).
4번과 5번을 겪고 나서 얻은 결론은 하나다 — **8GB 호스트에서는 "무엇을 쟀는가"만큼 "어떤 상태에서 쟀는가"가
수치를 좌우한다.** 그래서 스냅샷 복원·쿨다운·메모리 반환을 전부 프로토콜에 적어 둔다.

### 부하 생성기 격리 한계 (§9.3 — 숨기지 않고 밝힌다)

k6는 호스트에서 8코어를 애플리케이션과 공유한다. **완전한 격리는 불가능하다.**
측정 중 5초 폴링으로 CPU를 기록했다(`{코호트}-run1.cpu.log` · `ps`의 %CPU라 8코어에서 이론 최대 800%).

| 코호트 | java 평균 | java 중앙값 | k6 평균 | k6 최대 | (참고) M0 k6 평균 |
|---|---|---|---|---|---|
| `heavy` | 42.3% | 5.4% | **2.0%** | 3.5% | 7.6% |
| `normal` | 74.1% | 9.7% | **4.1%** | 8.8% | 5.5% |
| `light` | 68.8% | 10.9% | **6.9%** | 42.0% | 12.2% |

- **평균과 중앙값이 크게 벌어지는 것은 워밍업 구간 때문이다.** 로그는 앱 기동 직후부터 시작하는데,
  이때 풀스캔·JIT로 java가 700%대를 찍는 샘플이 서너 개 들어간다(`heavy-run1.cpu.log` 02:41:17~02:41:27).
  사다리 본 측정 구간의 실태는 중앙값 쪽이다. M0과의 비교를 위해 같은 방식의 평균도 함께 남긴다.
- **k6 경합은 M0보다도 낮았다** — heavy에서 평균 2.0% / 최대 3.5%다. 부하 생성기가 수치를 지배한 구간은 없다.
  `SharedArray` 도입으로 VU마다의 파싱이 사라진 것과 방향이 일치한다(실패한 시도 4).
- heavy에서 java CPU가 세 코호트 중 여전히 가장 낮다(중앙값 5.4%). **병목은 앱 CPU가 아니다** — M0과 같은 결론이다.

### 2. 최대 RPS (p99 < 200ms · 중앙값 기준)

| 코호트 | 최대 RPS | 근거 |
|---|---|---|
| `heavy` | **없음** | 최저 단계인 2 RPS에서 p99 522ms — 불성립. 단 20 RPS까지 **실패율 0%**로 처리 자체는 된다 |
| `normal` | **엄밀히는 없음** | 5~20 RPS 전 구간 p99 213~229ms — **경계 바로 위에서 평평하다** |
| `light` | **150+** | 사다리 상한(150 RPS)에서 p99 121ms 성립 — **상한을 못 찾았다** |

**`normal`의 "엄밀히는 없음"은 M0보다 나빠졌다는 뜻이 아니다.**

| | M0 | M1 |
|---|---|---|
| 10 RPS | p99 **132ms** — 성립 | p99 213ms — 불성립 |
| 20 RPS | p99 **549ms** — 붕괴 | p99 **229ms** — 여전히 평평 |
| 40 RPS | p99 834ms | p99 421ms |

M0는 10 RPS에서 기준선을 통과한 뒤 20 RPS에서 4배로 꺾였다. M1은 **기준선을 살짝 넘는 대신 40 RPS까지 완만하다.**
성립 여부라는 이진 판정만 보면 M1이 진 것처럼 보이지만, 곡선의 모양은 반대다.
**"최대 RPS" 한 숫자만으로는 이 차이를 표현할 수 없다는 것이 이 표의 교훈이다.**

`light`는 사다리 상한까지 성립해 **포화점을 찾지 못했다** — M0는 100 RPS에서 멈췄다(150 RPS p99 680ms).

### 5. buffer pool 히트율 — 하향 트리거 판정

| 구간 | 측정 구간 차분 히트율 | 판정 |
|---|---|---|
| saturation 9런 + `slo` 1런 **전부** | **1.0000** | 게이트(95%) 통과 — **하향 트리거 미발동** |

- 히트율 = `1 − (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)`, **런 전/후 차분**으로 산출
  (`SHOW GLOBAL STATUS`는 서버 기동 이후 누적이라 복원 직후 cold 읽기가 섞인다)
- 예: `heavy-run1.hitrate.txt` — delta reads **12** / delta read_requests **137,506,050**
- **게시글 300만을 그대로 유지한다.** 200만 하향(§8 · §4.6)은 M0에 이어 M1에서도 발동하지 않았다.
- M0의 "≥ 99.9%"에서 소수점이 더 붙었다. 함의는 M0과 같고, M1에서는 더 강하다 —
  **읽기 요청이 1억 3천만 건인데 디스크로 내려간 것이 12건이다. 병목은 I/O가 아니다.**

## 원인 분석

대상 쿼리는 M0과 **문자 그대로 동일**하다(§4.3 Pull SQL).

```sql
SELECT p.* FROM posts p
JOIN follows f ON p.author_id = f.followee_id
WHERE f.follower_id = :userId
  AND p.id < :cursor
  AND p.is_deleted = false
ORDER BY p.id DESC LIMIT 25
```

### 1. `EXPLAIN ANALYZE` (후보 B 적용 · heavy)

```
Covering index lookup on f  (501행)
  → Nested loop
    → Index lookup on p using idx_posts_author_deleted_id_desc
        (author_id = ?, is_deleted = false — 둘 다 인덱스 조건)
      → Sort: p.id DESC, limit 25            ← 남아 있다
```

| | M0 | **M1** |
|---|---|---|
| `p` 접근 | `fk_posts_author` ref + **별도 Filter 단계**(`is_deleted`) | `idx_posts_author_deleted_id_desc` lookup · **Filter 단계 소멸** |
| **정렬 입력 행수** | **14,963행** | **14,963행 — 동일** |
| 정렬 단계 | 존재 | **존재** |
| 서버 내부 시간 | 409ms | 345ms |

**바뀐 것은 행당 비용이고, 바뀌지 않은 것은 행수와 정렬이다.**
`is_deleted` 필터가 인덱스 조건으로 흡수되면서 행마다 테이블을 들춰 확인하던 단계가 사라졌다.
그 결과 단건 409ms → 345ms(−16%). **그러나 여전히 25건을 돌려주려고 14,963행을 읽어 정렬한다.**

### 2. 왜 `Sort`가 사라지지 않았는가

후보 A·B 모두 노렸던 것은 filesort 제거였고, **둘 다 실패했다.** 이유는 인덱스의 문제가 아니라
**조인 방향의 문제**다.

```
현재 계획 (follows 주도)
  follows에서 내가 팔로우한 author 501명을 꺼낸다
    → author마다 posts 인덱스를 lookup → 그 author 안에서는 id DESC로 정렬돼 나온다
      → 그런데 author가 501개다 → 501개 정렬열을 하나로 합쳐야 한다 → 전역 병합 정렬
```

**author별로는 정렬이 공짜인데, author 간에는 아니다.** `ORDER BY p.id DESC LIMIT 25`를 인덱스만으로
끝내려면 계획이 반대여야 한다 — **`posts`를 id 내림차순으로 스캔하면서 각 행의 author가 내 팔로잉에
있는지 확인하다가 25건이 차면 멈추는** 역방향 계획이다. 그러면 정렬도 없고 조기 종료도 된다.

옵티마이저는 그 계획을 택하지 않았다. **팔로잉 밀도가 낮기 때문이다.**

```
팔로잉 500명 / 전체 사용자 100,000명 = 0.5%   (작성자는 전 사용자 균등 랜덤 — 로드맵 P1-04)
→ posts를 id DESC로 훑으면 평균 200행에 1건꼴로 내 팔로잉의 글이 나온다
→ 25건을 채우려면 수천 행을 훑으면서 행마다 follows를 확인해야 한다
```

그리고 옵티마이저가 이 역방향 계획과 비교한 상대는 **현재 계획의 실제 비용이 아니라 추정치**였다.
M0에서 확인한 그 추정치가 `filtered 5.00%` 기준 **770행**이고, 실측은 **14,963행 — 19배 괴리**다(m0.md).
**비교의 한쪽이 19배 싸게 잡힌 채로 이뤄진 선택이다.**

> **한계를 명시한다 — 역방향 계획을 힌트로 강제해 실제로 재보지는 않았다.**
> M1의 범위는 "인덱스를 넣으면 어떻게 되는가"이고, **인덱스를 넣어도 옵티마이저가 계획을 바꾸지 않았다는
> 사실 자체가 이 절의 결론**이다. 힌트로 계획을 강제하는 것은 인덱스 도입이 아니라 쿼리 재작성이며,
> 그 방향은 Phase 2a의 Push가 대신 답한다.

**"인덱스로 filesort를 없앤다"는 M0 시점의 가설은 반증됐다.**
JOIN이 follows 주도인 한 전역 정렬은 남고, 후보 A·B 어느 쪽도 이 구조를 바꾸지 못했다.
(부록 B "posts 채택 인덱스 (P1-13)"에 이 구조적 결론을 등재했다.)

### 3. 그렇다면 클라이언트 지연은 왜 116배 좋아졌는가

서버 내부는 16% 좋아졌는데 클라이언트 p50은 31,636ms → 273ms다. **모순이 아니라, 두 수치가 재는 대상이 다르다.**
M0가 이미 답을 적어 두었다 — `클라이언트 지연 − 서버 내부 지연 = 큐잉 시간`(§9.3).

```
M0                                    M1
409ms 짜리 쿼리가 커넥션을 점유        345ms + 행당 비용 절감으로 점유 시간 단축
  ↓                                     ↓
풀 10개가 1 RPS에서 이미 소진          20 RPS까지 소진되지 않는다
  ↓                                     ↓
대기 30초 타임아웃 → 500 연쇄           대기 자체가 발생하지 않는다
  ↓                                     ↓
p50 = 타임아웃 상수 30,000ms           p50 = 실제 처리 시간 184~273ms
```

**M0의 30초는 쿼리 시간이 아니라 HikariCP 대기 타임아웃 값이었다.** 그 상수가 사라지자
지연이 두 자릿수 배로 줄어든 것처럼 보인다. 실제로 줄어든 것은 **큐잉이지 쿼리가 아니다.**

이것이 M1 개선의 정체다.

| 무엇이 | 얼마나 |
|---|---|
| 행당 접근 비용 | 줄었다 (Filter 단계 소멸 · 409 → 345ms) |
| 커넥션 점유 시간 | 줄었다 → **풀 고갈 임계가 1 RPS 미만에서 20 RPS로 이동** |
| **읽고 정렬하는 행수** | **그대로다 (14,963행)** |

**개선은 "덜 읽어서"가 아니라 "같은 양을 조금 더 싸게 읽어서" 나왔다.**
그래서 붕괴는 사라졌지만 지연의 바닥은 내려가지 않았다.

### 4. 병목은 여전히 I/O가 아니다

buffer pool 차분 히트율이 전 런 **1.0000**이다(`heavy-run1` 기준 읽기 요청 1억 3,750만 건 중 디스크 읽기 12건).
**데이터는 전부 메모리에 있는데도 heavy p99가 500ms를 넘는다.** 남는 후보는 M0과 같이 CPU와 정렬이고,
`EXPLAIN ANALYZE`가 그쪽을 가리킨다 — 다만 M0에서는 "정렬 + 행당 테이블 접근"이었고
M1에서는 **정렬만 남았다.**

### 5. 계측 수치 해석 시 주의

M1에는 서로 자릿수가 다른 세 종류의 "heavy 단건 시간"이 있다. **빼거나 나누기 전에 무엇을 잰 값인지 봐야 한다.**

| 값 | 무엇을 잰 것인가 |
|---|---|
| 345ms | `EXPLAIN ANALYZE` — 계측 오버헤드 포함, 후보 A/B **상대 비교용**으로 같은 조건에서 잰 값 |
| 29ms | 워밍업으로 30회 두드린 **대표 1명**의 API warm 단건 (`meta.txt`) |
| 273ms | 본 측정 p50 — 코호트 **1,000명 무작위 순회** + 큐잉 포함 |

같은 쿼리라도 **어느 사용자를, 어떤 캐시 상태에서, 몇 명을 돌아가며 재는가**에 따라 열 배가 갈린다.
이 리포트에서 코호트별 수치를 항상 함께 적는 이유다.

### 6. 이번에 새로 인용하지 않은 도구 — slow log · JFR

M1의 병목 판정 근거는 **`EXPLAIN ANALYZE`(계획·행수 비교) · 단계 표 · CPU 로그 · buffer pool 히트율**이다.
slow log와 JFR은 M1에서 **새 수치로 인용하지 않는다.** 숨기는 것이 아니라 다음 이유에서다.

- **slow log**: M0가 기록한 낭비 배율(`Rows_examined` p50 15,606 vs 반환 25건 — 약 600배)은
  **정렬 입력 행수가 14,963행으로 동일한 이상 구조적으로 같다.** 같은 행수를 읽으므로 새로 재도 같은 배율이다.
- **JFR**: M0에서 이미 "앱 CPU가 아니라 DB측 + 큐잉"이라는 결론이 나왔고, M1에서도 java CPU 중앙값이
  세 코호트 중 heavy가 가장 낮다(5.4%). 녹화 파일은 원시 결과로 남겨 두었다(로컬 보존).

**M1에서 재판정이 필요했던 것은 "병목이 어디인가"가 아니라 "인덱스가 그 병목의 무엇을 줄였는가"였고,
그 질문에 답하는 도구는 `EXPLAIN ANALYZE`의 계획 비교다.**

## M1이 충분하지 않았던 이유

**M1은 붕괴를 없앴지, 목표를 달성한 것이 아니다.**

### 1) 목표선까지 2.5~5배가 남았다

| heavy 단계 | p99 | 목표(200ms) 대비 |
|---|---|---|
| 5 RPS (최선) | 492ms | **2.5배** |
| 2 RPS | 522ms | 2.6배 |
| 10 RPS | 681ms | 3.4배 |
| 20 RPS | 827ms | 4.1배 |
| 15 RPS | 1,007ms | **5.0배** |

**최선의 조건에서도 2.5배다.** 그리고 **주입을 더 낮춘다고 나아지지도 않는다** — 최저 단계(2 RPS)가
최선이 아니라 5 RPS가 최선이다. s0가 s1보다 나쁜 것은 사다리 첫 단계라는 위치 효과일 수 있으나,
어느 쪽으로 읽든 결론은 같다. **경합을 걷어내도 남는 하한이 존재한다.**

### 2) 남은 격차는 행당 비용이 아니라 행수에서 온다

```
M0 → M1에서 바뀐 것 : 행당 비용 (Filter 단계 소멸)         → 409ms → 345ms, -16%
M0 → M1에서 안 바뀐 것 : 정렬 입력 행수 14,963행            → 0%
```

인덱스라는 가장 큰 수단이 행당 비용에서 얻어낸 것이 **−16%**였다.
p99 492ms를 200ms 아래로 내리려면 **약 60%를 더 덜어내야 한다.**
**한 자릿수~10%대의 행당 비용 절감을 아무리 쌓아도 닿는 크기가 아니다.**

그리고 그 14,963행은 데이터 분포에서 직접 나온 수다.

```
정렬 입력 행수 ≈ 팔로잉 수 × 작성자당 평균 글 수
heavy   :  501 × 29.9  ≈ 14,963행
normal  :  101 × 30.3  ≈  3,061행
light   :   11 × 29.3  ≈    322행
```

**팔로잉 500명인 사용자가 타임라인 첫 페이지를 열 때마다 1만 5천 행을 읽어 정렬해야 한다는 것은
쿼리 최적화의 실패가 아니라 Pull 구조 자체의 성질이다.** 인덱스는 이 곱셈에 개입할 수단이 없다.

### 3) 구조적으로 인덱스가 닿을 수 없는 지점이다

앞의 "왜 Sort가 사라지지 않았는가"가 그 이유다. 정렬을 없애려면 조인 방향이 뒤집혀야 하는데,
팔로잉 밀도 0.5%에서는 뒤집힌 계획이 더 비싸다. **옵티마이저를 설득할 인덱스가 없는 것이 아니라,
설득해도 이득이 없는 데이터 분포다.**

세 코호트의 정렬 입력 행수는 M1에서도 **322 / 3,061 / 14,963행으로 M0과 같다.**
계획이 코호트에 따라 갈리지 않는다는 것은 M0에서 확인됐고(m0.md), 행수가 그대로인 이상 M1에서 달라질 이유가 없다.
**같은 계획에서 행수만 늘어나는 구조라면, 팔로잉 수가 늘 때 느려지는 것을 막을 방법이 쿼리 안에는 없다.**

### 4) 요약

| 질문 | M1의 답 |
|---|---|
| 인덱스로 붕괴를 막을 수 있는가 | **그렇다** — 실패율 83.9~97.5% → 0%, 상한 <1 → 20 RPS |
| 인덱스로 p99 200ms에 닿을 수 있는가 | **아니다** — 최선 492ms, 2.5배 부족 |
| 왜 못 닿는가 | 읽고 정렬하는 행수(팔로잉 수 × 평균 글 수)가 그대로이기 때문 |
| 더 나은 인덱스가 있는가 | 후보 A/B 실측 동률 · 둘 다 Sort 제거 실패 — **인덱스의 문제가 아니다** |

이것이 §9.2가 M1에 요구한 **"인덱스만으로는 한계가 있었다"의 실측 근거**다.

## 남은 문제

**조회 시점에 15,000행을 만지는 한, 인덱스 튜닝으로는 p99 200ms에 닿지 않는다.**

| 도구 | 관측 | 함의 |
|---|---|---|
| `EXPLAIN ANALYZE` | 정렬 입력 **14,963행 — M0과 동일** · Sort 잔존 | 인덱스가 줄인 것은 행당 비용뿐 |
| 단계 표 | heavy p99 492 ~ 1,007ms | 최선에서도 목표의 2.5배 |
| 실패율 / `slo` | 사다리 0% · 1,000 RPS에서 91.8% | 붕괴는 사라진 게 아니라 임계가 올라갔을 뿐 |
| buffer pool | 히트율 1.0000 | I/O가 아니다 — CPU/정렬이다 |
| 코호트 비교 | 행수 ∝ 팔로잉 수 (322 / 3,061 / 14,963) | 비용의 주체는 쿼리가 아니라 **구조** |

### 다음 (Phase 2a → M2/M3)

남은 비용은 **"조회할 때마다 계산한다"**는 Pull의 전제 자체에서 나온다.
그렇다면 답은 계산을 더 빠르게 만드는 것이 아니라 **계산 시점을 옮기는 것**이다.

```
Pull  (M0/M1) : 조회 1회 = 팔로잉 500명 × 평균 30건 = 15,000행 읽기 + 정렬
                → 읽기가 50배 많은 트래픽(§7.1 읽기:쓰기 50:1)에서 매번 지불한다

Push  (M2/M3) : 작성 1회 = 팔로워 수만큼 Sorted Set에 ZADD (쓰기 시점 1회)
                → 조회 1회 = Sorted Set 상위 25개 + MGET — 정렬 없음, 팔로잉 수와 무관
```

**읽기:쓰기가 50:1이라는 것이 이 전환의 근거다**(§7.1). 비싼 계산을 50번 반복하는 대신 1번으로 몰아넣는다.

Phase 2a에서 fan-out on write를 구현하고 **M2(cold 캐시) / M3(warm 캐시)**를 측정한다.
M1이 여기서 남긴 두 숫자가 그 측정의 분모다.

| 분모 | 값 |
|---|---|
| heavy p99 (최선) | **492ms** |
| 조회 1회당 정렬 입력 행수 | **14,963행** |

M3에서 확인할 것은 지연 감소만이 아니다. **팔로잉 수에 대한 의존이 사라지는가**(light/normal/heavy가
같은 수치로 수렴하는가)가 Push 전환의 진짜 성공 기준이다. Pull은 세 코호트가 322 / 3,061 / 14,963행으로
갈렸지만, Push의 조회 경로에는 그 곱셈이 없다.

> 다만 Push는 공짜가 아니다 — 인플루언서 1명의 작성이 팔로워 수만큼의 쓰기로 번지는 문제(§7.2),
> 캐시와 DB의 정합성(§9.4), Redis 1GB 제약(§4.6)이 새로 생긴다.
> **M1이 "인덱스만으로는 한계"의 근거이듯, M2/M3는 "Push만으로도 한계"의 근거가 될 것이다.**
> Phase 3의 Hybrid는 그 측정 뒤의 이야기이며, 지금 예단하지 않는다.
