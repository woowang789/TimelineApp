# 타임라인 서비스

> 이 README는 뼈대다. 각 절은 해당 Phase의 측정과 구현이 끝난 뒤 채운다.
> 목차의 원본은 `timeline-project.md` §10이며, 서술 원칙은 **문제 → 원인 분석 → 시도 → 해결 → 결과 → 남은 한계**다.
> **측정 수치는 실측 전까지 자리표시자(X, Y, Z)로 둔다.**

## 한 줄 소개

300만 건 데이터 환경에서 타임라인 조회 p99를 **X초 → Yms**로 개선한 프로젝트

> _(M0 / M3 측정 후 실제 수치 기입 — Phase 1, Phase 2a)_

## 이 프로젝트가 다른 캐시 적용 사례와 다른 점

> _(Phase 2b 재측정 후 기입)_

같은 기능을 Pull / Push / Hybrid로 세 번 구현하고 각각 측정했다는 점, 다음 단계로 간 이유를
수치와 EXPLAIN ANALYZE로 남겼다는 점, 인덱스만으로 해결하려다 실패한 지점(M1)의 수치와
해결하지 못한 한계까지 숨기지 않고 적었다는 점을 4개 항목으로 서술한다.

## 아키텍처

> _(Phase 4′에서 다이어그램 작성 — 로드맵 4′ ⑤)_

Pull / Push / Hybrid 각 구성의 요청 흐름과 fan-out 경로, Redis·MySQL·Kafka의 역할 경계를 다이어그램으로 넣는다.

## 기술적 도전과 해결

### 1. 팔로잉이 많을수록 타임라인이 느려지는 문제

> _(Phase 1 → Phase 2a에서 기입)_

상황(p99 X초) · 원인(JOIN 후 filesort, EXPLAIN ANALYZE 실측) · 시도(복합 인덱스 → M1에서 Z% 개선에 그침) ·
해결(Push fan-out on write) · 결과(p99 Yms) · 트레이드오프(쓰기 비용, Redis 메모리)를 순서대로 적는다.

### 2. Redis가 죽으면 Pull 폴백이 DB를 죽인다

> _(구현은 Phase 2a, 장애 주입 검증은 Phase 4′에서 기입)_

"폴백이 있다"와 "폴백이 버틴다"는 다른 문제라는 점을 캐시 스탬피드로 설명하고,
세마포어 · 중복 폴백 락 · negative cache · DB 보호 Circuit Breaker와 그 검증(부하 중 Redis SHUTDOWN 시
DB 생존 / 503 비율 / 복구 시간)을 적는다.

### 3. 비동기 처리 후 내 글이 보이지 않는 문제

> _(Phase 2b에서 기입)_

fan-out 지연으로 인한 read-your-own-write consistency 위반과, 본인 타임라인만 동기 처리로 분리한 해결을 적는다.

### 4. 캐시가 맞는지 어떻게 아는가

> _(Phase 2b에서 기입)_

Pull 결과와 Push 결과의 동등성을 CI에서 상시 검증한 방법, fan-out 중단 후 재처리해도 동등한지 확인해
멱등성을 실증한 과정, 불일치율을 성능 지표와 나란히 기록한 결과를 적는다.

### 5. 자료구조 선택 하나가 어디까지 규정하는가

> _(Phase 2a ~ Phase 3에서 기입)_

Sorted Set을 택한 이유가 커서 페이지네이션이 아니라 멱등성이었고, 그 덕분에 Kafka at-least-once로 충분했으며,
순서 보장이 불필요해져 파티션 키까지 포기할 수 있었다(핫 파티션 원천 차단)는 연쇄를 적는다.

## 측정 방법

> _(Phase 1 첫 측정 이후 기입, Phase 4′에서 확정)_

open model(constant-arrival-rate)을 쓴 이유와 closed model의 함정, M0~M4로 나눠 측정한 변수 통제,
부하 생성기를 분리하지 못한 한계와 그 영향을 적는다. 리포트 원본은 `docs/perf/`에 둔다.

## 이 문제의 일반화

> _(Phase 4′에서 기입)_

fan-out이 SNS 고유의 문제가 아니라 파생 데이터의 계산 시점을 쓰기와 읽기 중 어디에 둘 것인가의 문제임을 밝히고,
메시징 · 권한 전파 · 커머스 · 인프라(읽기 복제, CDN, CQRS Read Model, Materialized View)로 확장한다.
공통 난제는 fan-out 자체가 아니라 **분포의 쏠림**이며, Hybrid가 꼬리를 몸통과 분리 처리하는 일반해라는 결론을 적는다.

## 의도적으로 하지 않은 것

> _(Phase 4′에서 기입 — 근거는 마스터 §3)_

MSA · 프론트엔드 · QueryDSL · 2계층 로컬 캐시를 제외한 이유를 각각 한 줄로 적는다.
"몰라서 안 한 것"이 아니라 "문제는 인지하고 있으나 이 프로젝트의 목적에 비해 얻는 게 적어서 안 한 것"임이 드러나야 한다.
